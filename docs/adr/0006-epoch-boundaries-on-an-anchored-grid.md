# Epoch boundaries come off a stored anchor, and each epoch's end is copied onto the Pool

`begin_epoch` set the first epoch's `starts_at` to whatever second the operator first cranked the pool, and every epoch after it chained from the previous `ends_at`. The draw time was an accident of deployment: nobody chose it, nobody could tell a player when to come back, and the skip branch that restarted a whole-epoch-late operator at `now` rerolled it to a fresh arbitrary phase after every outage. The rebuild stores `epoch_anchor` on `Pool`. It is not a start time but a phase reference for the grid `anchor + k * epoch_seconds`, running in both directions, and every boundary is a point on it. A late crank lands where a punctual one would, an outage skips whole epochs rather than moving them, and the three cases the old code branched on collapse into one expression. A Sunday 16:00 UTC anchor sits on the hourly, daily and weekly grids at once, so a cadence change is one `set-params` and the anchor itself never has to move.

Paired with it, `Pool` gains `current_epoch_ends_at` and `previous_epoch_ends_at`, which duplicate `Epoch.ends_at`. `touch` used to rebuild both from `current_epoch_start + epoch_seconds`, so changing `epoch_seconds` silently moved the accrual clamp on the running epoch and the freeze point of the one before it, and a short first epoch has no length that sum can produce. Considered and rejected: reading the number from the Epoch account that already holds it, by passing that account into `touch`. `touch` runs inside `deposit`, `withdraw`, `buy_position` and every other instruction that moves a Player, so it would add an account to all of them, plus the PDA derivation on every client that builds one. Sixteen bytes on one account is the cheaper side of that trade.
